The screen's overall structure is solid: proper MVVM separation, correct @State/@FocusState usage, sealed UI state, UseCase-based validation, and protocol-based DI. However, a critical logic bug — a missing password field — means the form can never pass validation. The design-system contract is violated in several places: hardcoded color literals, magic-number padding, and system font usage. All user-facing strings are hardcoded English, violating the project's localization mandate. Keyboard dismiss-on-tap is missing, and the image ForEach uses a fragile offset-based ID that risks incorrect diffing. The architecture and state management are clean, but the above issues must be resolved before this screen can ship.

Detailed Findings

Stability & Crashes
CRITICAL LOGIC UI-01: Password field missing from form — validation will always fail — Lines 61–116 (Screen) / Line 9 & 34 (ViewModel)

The ViewModel declares var password: String = "", the canSubmit computed property requires !password.isEmpty, and validateRegistration() validates password strength (min 8 characters). However, the form UI has no password TextField or SecureField. The password string remains empty forever, so:

  • (a) canSubmit always returns false if checked.
  • (b) validation.password always returns .empty after the first submit attempt.

The user sees no password field, yet the submit action fires validation that silently fails on a hidden field. This is a ship-blocking bug.

Fix: Add a SecureField between the email and phone fields (or wherever the design specifies), wired to $viewModel.password with proper .focused, .submitLabel, and .textContentType(.newPassword). Add the field to the Field enum and update the focus chain. If the password is intentionally omitted (e.g. sent via email), remove it from the ViewModel, canSubmit, and the validation path.

// Add to Field enum:
private enum Field: Hashable {
    case restaurantName, email, password, phone, description
}

// Add after the email textField block (~line 78):
SecureField("", text: $viewModel.password)
    .font(SvFont.timeValue)
    .foregroundStyle(Color.svOnBackground)
    .textContentType(.newPassword)
    .focused($focusedField, equals: .password)
    .submitLabel(.next)
    .onSubmit { focusedField = .phone }
    .padding(.horizontal, SvSpacing.lg + SvSpacing.xxs)
    .frame(height: SvSpacing.inputHeight)
    .background(fieldBackground)

// Update email field next: .phone → .password
// Update phone field: add appropriate previous focus
MEDIUM LOGIC UI-02: ForEach uses \.offset as ID — incorrect diffing on removal — Line 170

ForEach(Array(viewModel.imageRefs.enumerated()), id: \.offset) means SwiftUI identifies images by their index position. When an image is removed from the middle of the array, the remaining items shift indices. SwiftUI may animate the wrong views, skip transitions, or show stale AsyncImage content because it thinks the item at index 2 is "the same" view that was previously at index 2 (now a different URL).

// Current — fragile
ForEach(Array(viewModel.imageRefs.enumerated()), id: \.offset) { index, url in

Fix: Use the URL itself (which is unique per image) as the stable identity.

ForEach(Array(viewModel.imageRefs.enumerated()), id: \.element) { index, url in
LOW LOGIC UI-03: Temp image files written but never cleaned up — Lines 517–520

loadSelectedPhotos writes each selected photo to FileManager.default.temporaryDirectory with a UUID filename but never deletes these files on form dismiss, submit success, or image removal. While iOS eventually purges temp files, heavy use (adding/removing images repeatedly) accumulates orphaned files within the session.

Fix: Delete the temp file in removeImage(at:) and on submit success or screen dismissal. Consider maintaining a cleanup array in the ViewModel.

Modern Standards & Architecture
HIGH STANDARDS UI-04: Hardcoded color literals in languageChip — Design system violation — Lines 287–293

The languageChip function uses raw Color(red:green:blue:) literals for green (0.35, 0.76, 0.42) and orange (1.0, 0.596, 0.0) states. These bypass the design system, don't support dark mode via the Asset Catalog, and are invisible to a global theme change. The project contract mandates all colors through Color.svXxx tokens.

// Current — hardcoded
.foregroundStyle(isSelected
    ? Color(red: 0.35, green: 0.76, blue: 0.42)
    : Color(red: 1.0, green: 0.596, blue: 0.0))

Fix: Add semantic color tokens to the Asset Catalog (e.g. svSuccess, svWarning or svChipActive, svChipInactive) with dark-mode variants, then reference them here.

.foregroundStyle(isSelected ? Color.svSuccess : Color.svWarning)
// ... and similarly for the .fill() backgrounds:
.fill((isSelected ? Color.svSuccess : Color.svWarning).opacity(0.1))
HIGH STANDARDS UI-05: All user-facing strings are hardcoded English — Localization violation — Multiple lines

The project mandates zero hardcoded user-facing strings — everything via String Catalogs (Localizable.xcstrings). The following are all hardcoded:

  • "Register Restaurant" (133)
  • "Restaurant Images" (149)
  • "Admin Email" (71)
  • "Phone Number" (80)
  • "Restaurant Name" (215)
  • "English" / "Icelandic" (218–219, 252–253)
  • "Description" (249)
  • "Opening Hours" (300)
  • "to" (329), "Closed" (335)
  • "Upload Document" (368)
  • "Tap to upload document" (383)
  • "JPG, PDF up to 5MB" (388)
  • "Submit for Approval" (103)
  • "Registration submitted!" (429)
  • Success body text (434)
  • "Back to Sign In" (441)

Additionally, errorKey(for:) at lines 505–506 returns English strings for .tooShort and .tooLong instead of localization keys.

Fix: Replace all with LocalizedStringKey references or String(localized:). For error strings, use proper keys.

// Examples:
Text("register.title")                        // was "Register Restaurant"
Text("register.images.title")                 // was "Restaurant Images"

// In errorKey:
case .tooShort(let m): return "form.error.too_short \(m)"
case .tooLong(let m):  return "form.error.too_long \(m)"
HIGH STANDARDS UI-06: Missing keyboard dismiss-on-tap — UX requirement violation — Form body (lines 61–116)

The project standards mandate .onTapGesture { focusedField = nil } on multi-field forms for tap-outside-to-dismiss. The form has .scrollDismissesKeyboard(.interactively) (good), but no tap gesture dismissal. Users who tap on non-interactive areas (labels, images section, spacing) cannot dismiss the keyboard without scrolling.

// Current — missing tap gesture
.scrollDismissesKeyboard(.interactively)

Fix: Add .onTapGesture on the ScrollView or its content VStack.

.scrollDismissesKeyboard(.interactively)
.onTapGesture { focusedField = nil }
MEDIUM STANDARDS UI-07: Magic-number padding values — Design system violation — Lines 197, 198, 231, 263, 264, 482

Multiple padding/margin values use raw numbers instead of SvSpacing tokens:

  • .padding(.top, 6) and .padding(.trailing, 6) — lines 197–198
  • .padding(.horizontal, 18) — lines 231, 482 (reusable textField)
  • .padding(.vertical, 14) — line 264

Fix: Map each value to the closest SvSpacing token, or add new named tokens if the values are intentional Figma measurements.

// 6pt: add a new token if needed
// static let imageOverlap: CGFloat = 6 in SvSpacing
.padding(.top, SvSpacing.xxs + SvSpacing.xs)   // or a new token

// 18pt: between lg (16) and xl (20) — needs a named token
// static let fieldHPadding: CGFloat = 18
.padding(.horizontal, SvSpacing.fieldHPadding)

// 14pt: between md (12) and lg (16) — needs a named token
.padding(.vertical, SvSpacing.fieldVPadding)
MEDIUM STANDARDS UI-08: System font used for back chevron and icons — Lines 127, 159, 189, 284, 381, 424

Several places use .font(.system(size: ...)) for SF Symbols. While SF Symbols don't use Poppins, the project standard is to define icon-size tokens in the design system rather than scattering raw .system(size:) calls. At minimum, line 127's back chevron (.system(size: 17, weight: .semibold)) is a repeatable pattern that should be standardized.

Fix: For SF Symbol sizing, add icon-size constants to SvSpacing or a dedicated icon-token enum. This keeps sizes grep-able and changeable in one place.

MEDIUM STANDARDS UI-09: Missing wide-width preview for iPad-readiness check — Lines 628–662

The project standards require every screen's #Preview block to include a larger-width preview (e.g. 1024×1366) that verifies the layout "does not break" on iPad dimensions. The current previews cover Empty, Submitting, Submitted, Error, and Dark mode — but no wide-width variant.

Fix: Add a wide preview:

#Preview("Register - Wide (no break)") {
    NavigationStack {
        RegisterRestaurantScreen(viewModel: .previewInstance())
    }
    .environment(AppRouter())
    .frame(width: 1024, height: 1366)
}
MEDIUM STANDARDS UI-10: Language chips are non-functional — Lines 218–219, 252–253

The languageChip("English", isSelected: true) and languageChip("Icelandic", isSelected: true) are rendered as static, non-tappable views with hardcoded isSelected booleans. The description section has them set to false. There is no tap handler, no state binding, and no ViewModel support for language toggling. This appears to be either a half-implemented feature or decorative-only UI. Non-interactive elements that look interactive are a UX anti-pattern.

Fix: If language switching is planned: add ViewModel state and wire up Button taps. If purely decorative/informational: add .accessibilityHidden(true) and consider using a different visual treatment that doesn't imply interactivity (e.g. plain text badges instead of chip shapes).

MEDIUM STANDARDS UI-11: sensoryFeedback trigger fires on both directions — Line 44

.sensoryFeedback(.success, trigger: viewModel.state == .submitted) fires when the boolean expression changes value. This works on the transition from false → true, but also fires on true → false (e.g. if the user navigates back and the state resets). The .sensoryFeedback modifier with a Bool trigger fires on any change of the trigger value, not only when it becomes true.

Fix: Use the overload with a condition closure, or use .onChange(of:) with an explicit guard:

.onChange(of: viewModel.state) { _, newState in
    if newState == .submitted {
        // Trigger feedback via a separate @State bool
        // or UINotificationFeedbackGenerator
    }
}
Logic & Efficiency
LOW LOGIC UI-12: TimeChip popover has no auto-dismiss after selection — Lines 594–607

The DatePicker inside the popover updates the time on every wheel change via onChange, but the popover stays open indefinitely. The user must tap outside to dismiss it. For a time-picker chip this is acceptable UX, but a "Done" button inside the popover would be more discoverable, especially with VoiceOver.

Fix (optional improvement): Add a toolbar with a "Done" button inside the popover, or auto-dismiss after a short delay.

LOW LOGIC UI-13: HourMinute.toDate() uses Date() as anchor — Line 620

calendar.date(bySettingHour: hour, minute: minute, second: 0, of: now) uses the current wall-clock date as the anchor. This is fine for the DatePicker binding since only .hourAndMinute is displayed, but if this function were ever used for comparison or persistence, the date component would be non-deterministic. Low risk given current usage, but worth noting.

Accessibility
LOW STANDARDS UI-14: Several interactive elements lack accessibilityHint — Multiple lines

While many elements have .accessibilityLabel (good), the following lack hints that would help VoiceOver users understand the action:

  • PhotosPicker "Add restaurant image" (167) — no hint about max count or format
  • Document upload button (404) — no hint like "Opens file picker for JPG or PDF"
  • TimeChip buttons — no label or hint at all; VoiceOver reads the time text but doesn't announce "Opens time picker"
  • Language chips (if made interactive) — need labels

Fix: Add .accessibilityHint() to each interactive element with a description of the resulting action.

// PhotosPicker
.accessibilityHint("Opens photo library. \(maxCount - viewModel.imageRefs.count) slots remaining.")

// TimeChip
.accessibilityLabel("Open time: \(time.formattedString)")
.accessibilityHint("Opens time picker")
LOW STANDARDS UI-15: SvCompactToggle missing accessibilityValue — Line 567

The toggle uses .accessibilityAddTraits(isOn ? [.isSelected, .isButton] : .isButton) which communicates the element type but not the current value. VoiceOver users hear "selected, button" or "button" but ideally should hear "On" / "Off" explicitly via .accessibilityValue.

Fix:

.accessibilityValue(isOn ? "On" : "Off")
