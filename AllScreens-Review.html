Overall Project Rating: 6.6 / 10

The codebase demonstrates strong architectural fundamentals: clean MVVM separation, sealed UI state enums, protocol-based DI, @FocusState keyboard management, and comprehensive preview coverage. However, three systemic violations affect nearly every screen: (1) hardcoded color literals bypassing the Asset Catalog (20+ instances across 10 screens), (2) zero localization — every user-facing string is hardcoded English, and (3) extensive magic-number padding instead of SvSpacing tokens. Two screens (ProfileScreen and OfferDetailScreen) completely bypass the design system, using system fonts and colors exclusively. A critical bug in RegisterRestaurantScreen (missing password field) blocks registration. These issues are fixable without architectural changes, but represent significant technical debt that will compound as the app scales.

Systemic Issues (Affect Multiple Screens)

Cross-Cutting Findings
CRITICAL LOGIC SYS-01: RegisterRestaurantScreen — Password field missing from UI

The ViewModel declares, validates, and requires a password field, but the form screen has no SecureField for it. password remains empty forever, so validation always fails silently. Registration is completely broken.

Affected: RegisterRestaurantScreen.swift, RegisterRestaurantViewModel.swift

HIGH STANDARDS SYS-02: Zero localization — All user-facing strings hardcoded English (17/17 screens)

The project standard mandates all user-facing text through Localizable.xcstrings. Every single screen uses hardcoded English strings. This blocks Icelandic localization (the primary market) and violates Apple's localization best practices. Estimated: 200+ strings to extract.

Affected: All 17 screens

HIGH STANDARDS SYS-03: Hardcoded Color(red:green:blue:) literals bypass design system (10/17 screens)

Raw color literals appear in 10 screens with 30+ instances total. These bypass the Asset Catalog, break dark mode, and are invisible to global theme changes. Worst offenders: LoginScreen (8 instances), ForgotPasswordScreen (4), ResetPasswordScreen (5), RegisterRestaurantScreen (2 in languageChip), HomeScreen, SearchScreen, DealDetailScreen, OfferPreviewScreen, ConfirmLocationScreen.

Fix: Add semantic tokens to the Asset Catalog (svPlaceholder, svInputBorder, svChipActive, etc.) with light+dark variants.

HIGH STANDARDS SYS-04: Magic-number padding/spacing instead of SvSpacing tokens (14/17 screens)

Raw numbers like .padding(.top, 33), .padding(.horizontal, 18), .frame(height: 270) appear throughout. Only SettingsScreen, SelectLocationScreen, and SplashScreen are mostly clean. This makes the spacing inconsistent and unmaintainable.

HIGH STANDARDS SYS-05: System fonts used instead of SvFont tokens (6/17 screens)

ProfileScreen and OfferDetailScreen use system fonts (.title2.bold(), .body, .subheadline, .caption) exclusively — zero SvFont tokens. LoginScreen, ForgotPasswordScreen, and ResetPasswordScreen inline .custom("Poppins-Regular", size: 15) instead of using the existing SvFont.timeValue token. AddOfferScreen uses .subheadline.weight(.semibold) in its section label and .caption / .caption2 in error text.

HIGH STANDARDS SYS-06: .foregroundStyle(.black) breaks dark mode (5/17 screens)

Several screens use .foregroundStyle(.black) for text and icons (Login, ForgotPassword, ResetPassword, ConfirmLocation headers). On dark backgrounds, black text becomes invisible. Should use Color.svOnBackground.

MEDIUM STANDARDS SYS-07: Missing keyboard dismiss-on-tap (4/17 form screens)

Only ResetPasswordScreen has .onTapGesture { focusedField = nil }. Missing from: LoginScreen, ForgotPasswordScreen, RegisterRestaurantScreen, AddOfferScreen. Users on these screens can't dismiss the keyboard by tapping outside fields.

MEDIUM STANDARDS SYS-08: Duplicated pinkBorderedField / errorKey(for:) across auth screens

The pink-bordered text field is independently implemented in LoginScreen, ForgotPasswordScreen, and ResetPasswordScreen. The errorKey(for:) mapping is copy-pasted in 4 screens. These should be shared design-system components (SvTextField already exists but isn't used).

MEDIUM LOGIC SYS-09: ForEach(enumerated(), id: \.offset) — fragile identity (2 screens)

RegisterRestaurantScreen (line 170) and AddOfferScreen (line 170) use array offset as identity. When items are removed from the middle, SwiftUI misidentifies views, causing stale images or wrong animations. Use id: \.element instead.

MEDIUM STANDARDS SYS-10: Missing wide-width preview (8/17 screens)

The project standard requires every screen to have a preview at 1024×1366 to verify no iPad breakage. Missing from: SplashScreen, LoginScreen, ForgotPasswordScreen, ResetPasswordScreen, OfferDetailScreen, OfferPreviewScreen, SelectLocationScreen, ConfirmLocationScreen.

MEDIUM STANDARDS SYS-11: Missing dark-mode preview (8/17 screens)

Missing from: SplashScreen, LoginScreen, ResetPasswordScreen, DealDetailScreen, AddOfferScreen, OfferDetailScreen, OfferPreviewScreen, ConfirmLocationScreen. Given that several screens use .foregroundStyle(.black), these would immediately reveal dark-mode bugs.

MEDIUM LOGIC SYS-12: .sensoryFeedback bool trigger fires on both transitions (3 screens)

ForgotPasswordScreen, ResetPasswordScreen, and RegisterRestaurantScreen use .sensoryFeedback(.success, trigger: viewModel.state == .someState). The trigger fires when the boolean changes in either direction (false→true AND true→false), producing a spurious haptic on state reset.

MEDIUM LOGIC SYS-13: Business logic leaking into View layer (DashboardScreen)

DashboardScreen computes profileViewsCount, activeOffersCount, and totalOffersCount (lines 114–137) by pattern-matching on viewModel.state and doing math in the View. This violates the strict ViewModel-only-coordinates rule.

LOW STANDARDS SYS-14: Temp image files from PhotosPicker never cleaned up (2 screens)

RegisterRestaurantScreen and AddOfferScreen both write selected photos to the temp directory but never delete orphaned files on image removal or screen dismissal.

LOW STANDARDS SYS-15: Hardcoded placeholder data left in production code (3 screens)

HomeScreen: "Manhattan, New York..." (line 68), "Burger Barn" (line 239), hardcoded sample images. DashboardScreen: "The Golden Fork" (line 85). DealDetailScreen: stats "1,245" / "158" (lines 165–166).

Per-Screen Notable Findings

1. SplashScreen — 83/100

Strengths: Minimal, clean, single-purpose. Good animation pattern. Issues: Fixed width: 220 should be a token. Missing size-class check and wide preview. No user-facing strings so localization is a non-issue. Best screen in the codebase.

2. EntryScreen — 71/100

Strengths: Excellent multi-device previews (SE, 15, Pro Max, iPad, Dark). Responsive taglineFont. Issues: GeometryReader at root (CLAUDE.md warns against). Magic numbers 20, 24, 28. "Terms of use" / "Privacy policy" are not tappable links. Missing accessibility labels on buttons.

3. LoginScreen — 59/100

Strengths: Password toggle with a11y label. FocusState chain. Custom curved header shape. Issues: Worst design-system compliance — 8 hardcoded color literals, 3 inline font declarations, .foregroundStyle(.black). No size-class check. No wide or dark preview. No keyboard-dismiss-on-tap. Duplicated pinkBorderedField.

4. ForgotPasswordScreen — 66/100

Strengths: Size-class check. All-state previews. Issues: .foregroundStyle(.black). 4 hardcoded color literals. Duplicated field component. Missing keyboard-dismiss-on-tap. Missing wide preview.

5. ResetPasswordScreen — 68/100

Strengths: .onTapGesture { focusedField = nil } (only auth screen that has it!). canSubmit button gating. Issues: Same color-literal / system-font / dark-mode issues as other auth screens. Missing wide+dark previews.

6. RegisterRestaurantScreen — 67/100

Strengths: Rich form with images, opening hours, document upload. Custom SvCompactToggle. Issues: CRITICAL Missing password field. Hardcoded language-chip colors. Non-functional language chips. ForEach offset ID. Detailed findings in the separate RegisterRestaurantScreen-Review.html.

7. HomeScreen — 74/100

Strengths: Best preview coverage (6 variants including wide+dark+map). Skeleton loading. Pull-to-refresh. Map mode with annotations. Filter chips with selection state. Issues: Hardcoded placeholder data ("Manhattan", "Burger Barn"). String-based color Color("ECD3D9"). Deal card uses hardcoded sample image. 769 lines — could benefit from extraction.

8. DealDetailScreen — 72/100

Strengths: .safeAreaInset bottom bar. Hero image with gradient overlay. Skeleton loading. Wide preview. Issues: Hardcoded trend colors (acknowledged TODO). Hardcoded stats values. Missing dark preview. Empty action handlers.

9. SearchScreen — 74/100

Strengths: Full state machine (idle/noResults/results). Recent searches with clear. LazyVStack. Keyboard auto-focus. Dark + wide previews. Issues: Hardcoded gradient background color. Color.white in chip background breaks dark mode.

10. DashboardScreen — 70/100

Strengths: Full state coverage. Skeleton shimmer. Pull-to-refresh. Dark + wide previews. Issues: Business logic in View (stat computations). Hardcoded "The Golden Fork". Delete button has no confirmation dialog. Color.black for text.

11. AddOfferScreen — 69/100

Strengths: Sheet pickers. Max-length clamping. Character count. Preview/publish flow. Wide preview. Issues: System fonts in section labels and error text. .foregroundStyle(.red) instead of Color.svError. ForEach offset ID. Missing keyboard dismiss + dark preview.

12. OfferDetailScreen — 49/100

Strengths: Confirmation dialog for delete. Menu for edit/delete. Issues: Completely bypasses design system — uses .title2.bold(), .body, .subheadline, .secondary, .green, .orange throughout. Loading state is a bare ProgressView() (no skeleton). Magic numbers everywhere. Missing wide+dark previews. Looks like a different app from the rest of the screens.

13. OfferPreviewScreen — 64/100

Strengths: Clean card preview. .safeAreaInset action bar. Issues: Hardcoded "Open now" colors (acknowledged TODO). Odd SvSpacing.xs + 1 pattern. Missing size-class check, dark, and wide previews.

14. SelectLocationScreen — 72/100

Strengths: Clean search with results/recent/no-results states. Chip pattern for recent. Issues: Missing dark + wide previews. All strings hardcoded. No keyboard dismiss on tap.

15. ConfirmLocationScreen — 66/100

Strengths: Map camera tracking. Pin overlay. Bottom card with confirm. Issues: Hardcoded color literals (acknowledged TODO). .foregroundStyle(.black). Missing dark + wide previews. No accessibility on map or pin.

16. SettingsScreen — 74/100

Strengths: Clean section-card pattern with pink accent bar. Proper logout flow. Dark preview. Issues: Missing wide preview. No confirmation for "Delete Account" or "Log Out". All strings hardcoded. Multiple TODOs.

17. ProfileScreen — 48/100

Strengths: State-based UI. Wide preview. Issues: Completely bypasses design system — uses system fonts, .secondary/.tertiary colors, magic-number spacing. Loading is a text-based ProgressView. Error state is unstyled. No dark preview. Appears to be a rough placeholder.

What's Done Well (Project-Wide)

#AreaObservation
1ArchitectureConsistent MVVM with sealed UiState enums across all screens. ViewModels hold state, Views are reactive. Zero business logic in Views (except DashboardScreen stats).
2DIProtocol-based injection via init on all ViewModels. DIContainer assembles dependencies. Preview factories on every ViewModel.
3State OwnershipCorrect @State var viewModel with State(wrappedValue:) init pattern on all screens. No ViewModel via @Environment.
4Size Class15/17 screens read @Environment(\.horizontalSizeClass) at the root with a placeholder regular branch.
5Focus ManagementProper @FocusState with Field enums on all form screens. .submitLabel + .onSubmit chains for keyboard traversal.
6Loading StatesHomeScreen, DashboardScreen, DealDetailScreen, SearchScreen all have proper skeleton/shimmer loading states rather than bare spinners.
7NavigationRoute-based AppRouter used consistently. No inline-closure NavigationLink destinations.
8Preview CoverageEvery screen has at least one #Preview. 9/17 screens have 4+ preview variants covering multiple states.
9Empty StatesHomeScreen and DashboardScreen have proper empty states with illustrations and CTAs.
